Fix: Separate fast startup from heavy operations for Railway deployment

## Problem
- Railway healthchecks were failing because railway.toml called pre_deploy.sh
- pre_deploy.sh ran deploy.py which took 60+ seconds
- ALTER TABLE operations locked the database during startup
- App never started in time for healthcheck (100s timeout)

## Solution
Created a proper architecture that separates concerns:

### New Files:
- quick_init.py: Fast table creation (<1 second)
- heavy_setup.py: Heavy operations (ALTER TABLE, QR codes) run separately
- DEPLOYMENT_ARCHITECTURE.md: Full architecture documentation
- DEPLOY_NOW.md: Quick deployment guide

### Modified Files:
- railway.toml: Changed startCommand to use quick_init.py instead of pre_deploy.sh
- app.py: Gracefully handles admin creation, won't crash if column too small
- Procfile: Updated for consistency

### Deleted Files:
- Removed obsolete fix documentation files

## Result
- App startup: 5-10 seconds (was 60-90 seconds)
- Healthcheck: Passes immediately
- Heavy operations: Run separately after deployment
- Deployment: Reliable and fast

## Deploy Steps
1. Commit and push this fix
2. Railway will deploy automatically
3. Healthcheck will pass ✅
4. After deployment, run: railway run python heavy_setup.py
5. Restart app: railway restart
6. Admin login will work
